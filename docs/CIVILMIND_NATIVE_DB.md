# CivilMind Native DB (prototype)

CivilMind Native DB is a custom, embedded retrieval engine prototype. It is not a wrapper
around PostgreSQL, Qdrant, or another database. Its own WAL format is authoritative; its BM25
inverted index and exact flat cosine index are derived in-memory indexes rebuilt from the WAL.

## Scope of v0.1

- Append-only WAL with length-prefixed, SHA-256-checksummed frames.
- fsync before a mutation becomes visible in memory.
- Recovery by replaying sequential records.
- Truncate an incomplete final frame; fail loudly on a checksum mismatch in a complete frame.
- Chunk upsert/delete, metadata filtering, project scoping.
- BM25-like lexical scoring, exact cosine similarity, reciprocal-rank-fusion results.
- HTTP endpoints for ingest, delete, search, and stats.
- Bearer-token authentication when `CIVILMIND_DB_TOKEN` is configured.

## Run locally

```bash
CIVILMIND_DB_DATA_DIR=.data/civilmind-native CIVILMIND_DB_TOKEN=dev-token \
  .venv/bin/uvicorn civilmind.native_db.server:app --host 127.0.0.1 --port 8091
```

The example binds to loopback. Set a strong token before exposing it to another machine.
`/health` is intended for local health checks; data endpoints require a bearer token when configured.

## API

- `PUT /v1/chunks`: insert or replace a chunk (same ID means idempotent replacement).
- `DELETE /v1/chunks/{chunk_id}`: write a tombstone.
- `POST /v1/search`: accepts query, project ID, optional metadata filters, and an optional query embedding.
- `GET /v1/stats`: reports sequence, live chunk count, and WAL bytes.

Embeddings are generated by CivilMind's configured embedder, not by this engine.

## Limitations: not production ready

This is a single-process, single-node prototype. It has no multi-process file locking, replication,
compaction, WAL rotation, incremental snapshots, HNSW/ANN vector index, vector quantization,
per-tenant encryption, schema migration protocol, quotas, or comprehensive adversarial fuzzing.
The vector index is exact and linear scan. WAL replay reads records into memory before rebuilding
indexes, which caps the practical size of this implementation. Production use requires benchmarks,
compaction/snapshot design, cross-process locking, crash fault injection, and security review.

Do not treat this as a replacement for CivilMind's PostgreSQL business metadata until a deliberate
migration plan and parity tests exist. The first safe integration target is chunks and retrieval,
behind a storage interface, with existing stores retained for rollback.
