# CivilMind Native DB

CivilMind Native DB is a custom, single-node Go retrieval-engine prototype for construction-document chunks. It does not use PostgreSQL or Qdrant in the chunk-search path.

## What v0 implements

- Append-only, length-prefixed write-ahead log (WAL) with SHA-256 checksums.
- fsync before a mutation becomes visible in memory.
- Sequential replay, torn-final-record truncation, and fail-closed checksum validation.
- BM25-style lexical retrieval that preserves engineering terms such as IS:456, M-20, and 5.3.
- Exact cosine vector retrieval, project and metadata filters, and reciprocal-rank fusion.
- Revision identifiers and source evidence records.
- Standard-library Go HTTP server with bearer-token protection for data APIs.
- Unit tests for replay, corruption, search filters, vector validation, and HTTP auth.

## Run

From the repository root, configure these values in your local .env file:

- CIVILMIND_DB_DATA_DIR=.civilmind-native-db
- CIVILMIND_DB_TOKEN=a-long-random-secret
- CIVILMIND_DB_ADDR=127.0.0.1:8091

Then run:

- make native-db-test
- make native-db-run

The server binds to loopback by default. Do not expose the API to a network without TLS termination, a strong token, network policy, and a security review.

## API

PUT /v1/chunks inserts or replaces a chunk. DELETE /v1/chunks/{id} writes a tombstone. GET /v1/chunks/{id} fetches a chunk. POST /v1/search runs hybrid retrieval. POST /v1/evidence stores a source reference, and GET /v1/chunks/{id}/evidence lists evidence. GET /v1/stats reports engine state. GET /health is an unauthenticated liveness endpoint.

Example request to insert a chunk:

    curl -X PUT http://127.0.0.1:8091/v1/chunks \
      -H 'Authorization: Bearer your-token' -H 'Content-Type: application/json' \
      -d '{"id":"c12-r4-p12","project_id":"tower-a","document_id":"S-101","revision_id":"R4","content":"Column C12 width 600 mm","metadata":{"discipline":"structural"},"vector":[0.2,0.1,0.9]}'

Search embeddings must be generated by CivilMind's configured embedding model. The database stores and searches vectors but does not invoke an embedding model.

## Data and recovery model

The WAL is authoritative. Each record is JSON encoded, length-prefixed, checksummed, and ordered by a monotonically increasing sequence. Indexes are derived in-memory state and rebuilt from the WAL during startup. The engine truncates an incomplete final frame but refuses to start when a complete frame has an invalid checksum or sequence.

The vector search is exact O(N×D); the lexical index consumes RAM proportional to tokens and postings. This keeps v0 understandable and testable, not suitable for unbounded corpora.

## Validation

The repository CI workflow runs gofmt, race-enabled tests, and go vet against this module.

## Explicit non-goals of v0

No distributed replication, multi-process locking, concurrent multi-writer support across processes, WAL compaction, snapshots, ANN/HNSW index, vector quantization, database migration protocol, encrypted-at-rest records, or production-grade multi-tenant authorization. Use this first as an experimental retrieval backend with a rollback path, not as the only storage for business metadata.
